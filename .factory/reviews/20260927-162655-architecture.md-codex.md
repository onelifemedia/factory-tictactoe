## Verdict
AGREE-WITH-CONCERNS — the core/UI separation is appropriate, but deployment and rollback need concrete fixes to satisfy R-014.

## Findings
- [C1] [HIGH] §6 rollback — re-uploading `github-pages` conflicts with the artifact already uploaded by the failed deployment — same-name replacement requires explicit overwrite in [upload-artifact](https://github.com/actions/upload-artifact#overwriting-an-artifact) — upload the downloaded `artifact.tar` under a distinct rollback artifact name and pass that name to `deploy-pages`; preserve the tar without nesting it inside another tar.
- [C2] [HIGH] §§6–7 deployment — the build is not bound to the commit whose CI passed — `workflow_run` uses the latest default-branch commit as `GITHUB_SHA`, so CI for commit A can trigger deployment of newer, unverified B ([GitHub documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run)) — explicitly build `workflow_run.head_sha`, or deploy the artifact produced by that exact CI run; define the equivalent gate for manual dispatch.
- [C3] [HIGH] §6 retention — 90-day retention cannot guarantee the required rollback — after 91 days without deployment, the previous successful run still exists but its artifact has expired; the documented “no previous successful run” branch does not cover this — retain the latest successful deployment bytes durably, or obtain an explicit change to R-014 limiting the rollback guarantee.
- [C4] [MEDIUM] §2 computer player — board-only memoization needs an explicit cache lifetime — `OX.......` evaluates to an O win with O to move but a draw with X to move; both turns are possible with different starters, and root-relative depth also changes scores between searches — create a fresh cache per `chooseComputerMove` call, or include side-to-move and normalize cached scores; test successive games with alternating starters.
- [C5] [MEDIUM] §6 smoke test — a passing smoke test does not establish that the new deployment is live — during the explicitly anticipated propagation window, the previous working page can accept X and reply O, falsely marking the new deployment successful — embed a build identifier and require the expected identifier before testing gameplay.
- [C6] [MEDIUM] §6 concurrency — `concurrency: pages` does not queue every successful merge — with A running and B pending, arrival of C cancels B even without `cancel-in-progress`, violating R-014’s “every merge” wording ([GitHub documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)) — specify workflow-level queuing across deployment, smoke and rollback, including an overflow policy.
- [C7] [MEDIUM] §2 page — `<noscript>` covers disabled JavaScript but not a failed module download — with JavaScript enabled and the bundle returning 404, the PRD’s required failure message remains hidden — render a static fallback that successful initialization removes, and test a blocked bundle request.
