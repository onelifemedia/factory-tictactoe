# F-008: Make the game fully keyboard-playable with managed focus

- **Milestone:** M3 · **Size:** M · **Requirements:** R-007, R-006 · **Depends on:** F-007
- **Screens:** game-01 (focus on "You go first" after Play again), game-02 (roving focus, keyboard hint), game-03 (focus on "Play again")
- **Components:** roving tabindex, keyboard hint (`aria-describedby`), focus ring
- **Branch:** `factory/F-008-keyboard-and-focus` from `main` @ fdeb23c

## Acceptance criteria

1. Given a fresh page, when a test plays a full game using only Tab, Shift+Tab, arrow keys, Enter and Space, choosing "You go first", then it reaches a result. "Play again" then starts a second game choosing "Computer goes first", which also reaches a result.
2. Given the board has focus during play, when an arrow key is pressed, then focus moves one square in that direction and stays put at the board's edge, and exactly one square has `tabindex="0"` (the rest `-1`).
3. Given the choice, when "You go first" is chosen, then focus is on row 1, column 1. When "Computer goes first" is chosen, then focus is on the first empty square in reading order (row 1, column 2).
4. Given a move that continues the game, focus stays on the square played. Given a taken square, focus stays on it. Given game over, focus is on "Play again". After "Play again", focus is on "You go first".
5. Given any focused control, when its computed style is read, then its outline is at least 2 CSS px wide. During play the hint "Arrow keys move between squares. Enter or Space places X." is shown and referenced by every square's `aria-describedby` (Codex C2); outside play it is absent and the attributes are removed.

## Modules

- **`src/ui/focus.ts`** (pure, no DOM):
  - `nextSquareIndex(index, key)`: `ArrowUp`, `ArrowDown`, `ArrowLeft` and `ArrowRight` move one square on the 3×3 grid and stay at the edge. Any other key returns `null`.
  - `chooseFocusTarget(step)` returns a `FocusTarget` of `{ kind: "square", index }`, `{ kind: "play-again" }` or `{ kind: "first-choice" }`, or `null`:
    - `started`: the first empty square of the new board
    - `placed X` with the game continuing: that X's square
    - `rejected not-playing`: `null`, checked **first**, before any state rule (Codex spec review C3)
    - `rejected occupied`: that square
    - the state is `over`: "Play again"
    - `resetToChoosing()` (choosing with no events): "You go first"
    - anything else: `null`
  - The initial page load does not call it (main passes `null`), so nothing is focused until the player tabs.
- **`src/ui/view.ts`:**
  - `render(state, status, focusTarget)`.
  - **Roving tabindex** (the APG algorithm): the view keeps `activeIndex`. Every focus change, whether by arrow key, pointer (`focusin`) or render, updates the tabindex of both squares synchronously: the focused square gets `tabindex=0`, the previous one `-1` (Codex C1). During play exactly one square is `0`; outside play every square is `-1` and natively `disabled`.
  - A `keydown` listener on the board handles only the four arrow keys (`nextSquareIndex` ≠ null) and calls `preventDefault` only for them, so Tab, Enter and Space keep their native behaviour.
  - During play the action area holds `p#hint.hint`, and **each square** gets `aria-describedby="hint"`. Descriptions are not inherited from the group, so the focused button itself must reference the hint (Codex C2). Outside play the hint is removed and so are the attributes.
  - **Safari / WebKit:** the choice buttons and "Play again" get an explicit `tabindex="0"`. Safari's default setting ("Press Tab to highlight each item" off) skips `<button>` elements on plain Tab. A probe on 2026-09-27 found that plain Tab reached nothing in the webkit and mobile-iphone projects, and did reach "You go first" once `tabindex="0"` was set. Squares already carry an explicit tabindex (roving). So keyboard play works in Safari without changing settings, and the tests use plain Tab in every project.
  - Focus is applied last in `render`, after the action area is rebuilt.
- **`src/main.ts`:** `apply(step, focusTarget = chooseFocusTarget(step))`. The first render passes `null`.
- **`src/styles.css`:** `.hint` (small, text-muted, centred). The focus ring already exists: 3 px `:focus-visible`.

## Tests to write first

- **`tests/unit/focus.test.ts`:**
  - `nextSquareIndex` for all 9 squares × 4 arrows (edges stay), plus a non-arrow key returning `null`.
  - `chooseFocusTarget` for: start (human), start (computer, → 1), a continuing move, occupied, a win, a human-filled draw, a computer-filled draw, reset, and a `not-playing` rejection (→ `null`).
- **`tests/e2e/keyboard.spec.ts`** (all 5 projects). Keyboard input goes through `page.keyboard` only, and focus is asserted on `document.activeElement` / `toBeFocused`. No pointer, no locator-driven focus and no injected `.focus()` are used to drive play, and no project is skipped (Codex missing item).
  - A fresh load followed by plain Tab lands on "You go first" in every project, including webkit and mobile-iphone.
  - A two-game run: Tab to "You go first", then Enter. Arrow to and Space/Enter a real losing line (human squares 0, 1, 3 → a computer win). Focus lands on "Play again"; Enter. Focus is on "You go first"; Shift+Tab/Tab to "Computer goes first" and Enter. Play to a result (a real sequence), and focus is on "Play again".
  - Arrows: from row 2, column 2, each arrow moves one step; pressing into an edge keeps focus. Exactly one square has `tabindex=0` after each move.
  - Focus after each choice (1,1 and 1,2), after a move (the played square), after a taken square (stays), at game over ("Play again"), and after Play again ("You go first").
  - Focus-ring width at least 2 px for a square, a choice button and "Play again" when focused by keyboard.
  - The hint is visible during play, and the focused square's accessible description (`toHaveAccessibleDescription`) is the hint text. While choosing and after game over, the hint and every `aria-describedby` are absent.
  - Arrows move through both X and O squares. During play every square is natively enabled (`disabled === false`). Enter on an occupied square leaves the board unchanged and focus stays. Outside play, no square is tabbable.
  - Tab out of the board and Shift+Tab back returns to the last active square, including when that square is occupied.
  - Pointer to keyboard: after clicking a square (the one pointer step, used only for this sync test), that square is the only `tabindex=0` square and arrows start from it.
  - After every arrow press, the focused square is the only square with `tabindex="0"`.
  - A fresh load has no focused square or button (`document.activeElement` is `body`).

## Approach

The focus decisions are pure and unit-tested (`focus.ts`); the view applies them. Rendering never re-creates squares, so focus is never lost to `body` during play (architecture §5, ADR-012).

## Spec review (before coding)

Codex: AGREE, with 3 medium and 4 missing, all accepted:
- C1: synchronous roving tabindex on every focus change
- C2: the hint is described per square
- C3: `not-playing` returns `null` first
- Missing: `preventDefault` only for arrows; X/O navigation, enabled squares and occupied Enter; Tab exit and return, and pointer-to-keyboard sync; proof of WebKit Tab entry. The probe showed plain Tab skips buttons in WebKit, fixed with an explicit `tabindex="0"` (see Modules).
