# F-003: Build the perfect computer player and the exhaustive never-lose test

- **Milestone:** M2 · **Size:** S · **Requirements:** R-003 (primary metric: 0 computer losses) · **Depends on:** F-002
- **Screens:** none (pure game core, ADR-009, ADR-010)
- **Branch:** `factory/F-003-perfect-player`, stacked on `factory/F-002-board-model` (PR #3)

## Acceptance criteria

1. Given both starting sides, when a test enumerates every legal human move at every human turn and applies `chooseComputerMove` at every computer turn, then no finished game is an X win, and the test reports the finished-game count (greater than 0) per starting side.
2. Given any reachable position where O can complete three in a row, when the computer chooses, then it completes a line.
3. Given the same position twice, when the computer chooses, then it returns the same square. It is deterministic: ties go to the lowest index, and the opening move on an empty board is index 0.
4. Given successive enumerations in one process with alternating starters, when they run, then the results equal those of fresh runs, because the memo keyed by board plus side to move stays valid.
5. Given CI, when the unit job runs, then the exhaustive test finishes in under 60 seconds.

## Tests to write first

- `tests/unit/never-loses.test.ts`:
  - **Enumeration:** a recursive walk from the empty board, once with the human (X) starting and once with the computer (O) starting. At the human's turn it branches on every empty square; at the computer's turn it applies `chooseComputerMove`. It stops at `evaluateResult` ≠ null (F-002).
  - **Per starting side:** it asserts 0 finished games won by X and a count of finished games greater than 0, and reports the counts with `console.info` (e.g. `human first: N games, 0 losses`).
  - **Timing:** the whole enumeration for both starters must take under 60,000 ms, measured with `performance.now()`.
  - **Memo across starters:** run the enumeration human, computer, human, computer in one module instance. Compare its outcome summary (a sorted list of the final boards plus results) with running each starter on a fresh module instance (`vi.resetModules()` and a dynamic `import()`). They must be identical.
- `tests/unit/computer-player.test.ts`:
  - **Takes the win:** for every reachable position (collected by the same enumeration) where O has at least one move that completes a line, the chosen square completes a line.
  - **Deterministic:** the same board twice gives the same square, for every reachable O-to-move position.
  - **Opening:** `chooseComputerMove(createEmptyBoard())` returns 0.
  - **Tie-break sanity:** after X at the centre (index 4), O replies with the lowest-index corner (0). After X at 0 and X at 8 with O at 4, O replies at 1 (the edge), matching the design's sample game.
  - **No legal move:** on a full board or an already-won board, `chooseComputerMove` throws a `RangeError`.

## Approach

`chooseComputerMove(board: Board): number` is called when O is to move:
- **Search:** full-depth minimax over `emptySquares`. A position's value is node-relative from O's point of view:
  - `+10` for a finished O win and `-10` for an X win, measured at the node.
  - A parent takes the best child value moved one step toward 0: `v > 0 → v − 1`, `v < 0 → v + 1`, `0 → 0`. So `10 − plies to the end` for an O win, `plies to the end − 10` for an X win, and 0 for a draw (ADR-010).
  - O maximises and X minimises.
- **Memo:** values are cached in a module-level `Map` keyed by the 9-character board string plus the side to move. Because values are node-relative they stay valid across searches, games and starters (at most 2 × 3⁹ keys).
- **Choice:** the empty square with the highest child value; ties go to the lowest index. It throws `RangeError` when the game is already over.
- No DOM, no randomness, no exported test hooks: the fresh-module comparison uses `vi.resetModules()`.
